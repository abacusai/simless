# Findings

These are the platform facts behind simless's design, found by building it against a large production SwiftUI app on Xcode 27 / macOS 27 (Apple Silicon, 32 GB). Each one cost time to discover; they are recorded so nobody has to rediscover them.

## Why not the simulator

- **Memory:** a booted iOS 27 simulator running a real app holds about **2.2 GB of private memory across ~210 processes** (5 simulators: 11.2 GB, 1,071 processes; see [benchmarks](benchmarks.md)). One `xcodebuild` UI-test run with parallel testing clones and boots several of them. During development we observed **one agent's single UI-test run with 3 cloned simulators running**, and 556 simulator processes on the machine in total.
- **Compilation:** each agent also runs its own full `xcodebuild`, and each one wants every core.
- **Why it breaks down:** with 4–5 agents, a 32 GB Mac starts swapping. The bottleneck is "N × (build + simulator)", not any single tool.

## Rendering approaches that don't work

- **`ImageRenderer`:** it only rasterizes SwiftUI primitives. Complex controls, `ScrollView` content, `List`, `Picker`, `Map` and UIKit-backed views render as placeholders or blank, so it can't render real screens.
- **Single-file renderers** (render a `View` from one `.swift` file) can't load a real app's modules and dependencies.
- **Xcode's `RenderPreview` (MCP)** renders real previews, but needs the Xcode GUI per project and uses a simulator runtime underneath.
- **Mac Catalyst** needs `ios-macabi` slices from every SDK, and many closed-source SDKs don't ship them. Designed-for-iPad runs the iOS slice unchanged.

## Designed for iPad: the details

- **Hidden destination:** Xcode hides the "Designed for iPad" destination for targets with `macosx` in `SUPPORTED_PLATFORMS`. Command-line build-setting overrides don't bring it back; the project file itself must change, so simless uses a generated copy.
- **Destination string:** `xcodebuild` can't parse `variant=Designed for [iPad,iPhone]` (the comma breaks the destination parser). `variant=Designed for iPad` works.
- **Launching:** `open` on the built `.app` fails ("incorrect executable format"), and so do a hand-made wrapper bundle and running the binary directly. **The only supported installer is `xcodebuild test`**, which goes through `installcoordinationd`. A zero-test run (`-only-testing:<Target>/NonExistent`) installs, launches, runs nothing and exits 0.
- **Installed copies are read-only.** They live under `/var/folders/.../d/Wrapper/` on a read-only filesystem.
- **Stale registrations:** LaunchServices can hold several registrations for one bundle id, and `open -b` may pick a stale one. Launching the slot's `.XCInstall/<App>.app` wrapper by path is reliable.
- **Startup race:** `open` right after the install run can be swallowed while the install's test process is still exiting. Wait until no instance of the bundle id is running, then launch.
- **Builds under `/tmp` are killed by Gatekeeper** ("Gatekeeper policy blocked execution"). The same build under `~/Library/Caches` runs.
- **One instance per bundle id:** launching a second host of the same app kills the first. Concurrent installs of the same bundle id fail ("Coordinator found for …"). Hence one bundle id per slot, and serialized installs.
- **Signing without the developer account:** the team's wildcard development profile (`TEAM.*`), which already lists the Mac's provisioning UDID, is enough once capabilities are stripped. Nothing gets registered.
- **Supervisor cost:** a host running *inside* an XCTest (the first prototype) keeps an `xcodebuild` alive at about **500 MB RSS**, and killing it kills the host. Moving the server into the app and launching with `open` removed it. The host's own footprint is **~30–35 MB**.
- **Scheme containers are relative to the project's directory.** A scheme in `ios/App.xcodeproj` says `container:App.xcodeproj`, not `container:ios/App.xcodeproj`. If a copied scheme isn't rewritten to match, it silently builds the original project's targets.
- **Reading build settings:** `xcodebuild -showBuildSettings -scheme X -sdk iphoneos` fails for some schemes ("Found no destinations"). Querying with the actual destination (`-destination 'platform=macOS,arch=arm64,variant=Designed for iPad'`) works, and `-target` works as a fallback, but `-target` can't take `-derivedDataPath`.
- **Swift 6 data-race errors don't appear with `-typecheck`.** Region-based isolation is checked later in compilation, so code that typechecks can still fail to build in Swift 6. Check templates by compiling them, in every language mode they must support.
- **Test plans** reference targets as `container:<Project>.xcodeproj`. Building from a renamed project copy yields an empty `.xctestrun` unless the plan is copied and rewritten too.

## The native mode: the details

- **The platform tag is the whole difference.** An iOS device binary with its `LC_BUILD_VERSION` platform changed from iOS (2) to Mac Catalyst (6), and signed ad hoc, runs as a plain Mac process: no provisioning profile, no install, no LaunchServices. Building for Mac Catalyst instead fails on SDKs without `ios-macabi` slices, but retagging the built binary doesn't care what the SDK shipped.
- **Every image in the process needs the tag.** dyld won't load an iOS-tagged dylib into a Mac Catalyst process, so patches, test bundles and SimlessRuntime are retagged too. Frameworks from Xcode's Mac platform folder (XCTest) are zippered and load as they are.
- **Signing the changed binaries one by one is enough** to run, and one `codesign -s -` call for all of them takes ~30 ms for the demo app. `DYLD_INSERT_LIBRARIES` works, since an ad hoc signature without the hardened runtime has no library validation.
- **`isiOSAppOnMac` is false under Mac Catalyst** (`isMacCatalystApp` is true in both modes). `ProcessInfo.processInfo` is a private subclass, `_NSSwiftProcessInfo`, with its own getter, so overriding `NSProcessInfo`'s did nothing. SimlessRuntime replaces it in every class of the hierarchy.
- **A native host's sockets can be closed under it.** A listening socket SimlessRuntime opened early failed `accept` with `EBADF`, then `ECONNABORTED`, and the thread spun at 100% CPU. A plain Mac program with the same code was fine, and other descriptors opened at the same time survived. It also happens later and to sockets moved to numbers from 1000 up: in a full UI run of the production app, five hosts lost their listener, and that run had seven flaky tests against none in runs that lost none. While a host listens again, a request in flight is lost: a tap or a drag that never happened, a screenshot that came back empty. What closes them wasn't found. The runtime listens again when its socket goes (closing the old descriptor only while it's still its own), and every UI test request carries an id: the shim sends it again on a new connection, and the runtime answers a repeated id from its first attempt, so nothing runs twice and nothing is lost.
- **`NSTemporaryDirectory` ignores `TMPDIR`** in an unsandboxed app and reads `confstr(_CS_DARWIN_USER_TEMP_DIR)`, the user's shared `/var/folders/…/T`. Interposing `confstr` gives each slot its own tmp. `CFFIXED_USER_HOME` is honored by `NSHomeDirectory` and `FileManager`'s folders.
- **Preferences ignore `CFFIXED_USER_HOME`.** cfprefsd writes `~/Library/Preferences/<bundle id>.plist`, so a slot's preferences are keyed by its id and cleared through CFPreferences (deleting the file behind cfprefsd's back hands the next launch its cached values).
- **The keychain refuses every call** without an application identifier: `errSecMissingEntitlement` (-34018), for the file-based and the data protection keychain alike.
- **A Mac process keeps the memory it frees.** After 48 renders a native host had 42 MB of dirty malloc pages against 21 MB for a "Designed for iPad" one, with the same live heap (27.6 and 28.2 MB). `malloc_zone_pressure_relief` returns 0 with the xzone allocator. `MallocSpaceEfficient=1` gives the iOS behavior: 36 and 37 MB, renders as fast. It isn't free for CPU-bound code: a test target that runs ~270 s took 278 to 283 s with it and 268 s without (270 s as "Designed for iPad"), so only render hosts get it. `MallocXzoneDeferSmall`, `MallocXzoneDeferTiny`, `MallocDeferredReclaim` and `MallocXzoneSegmentDeallocate` returned nothing.
- **No window server needed.** In a launchd job limited to the Background session (no Aqua session, like SSH or a LaunchDaemon's user job) the app runs, but no scene ever connects. A `UIWindow(frame:)` with no scene still lays SwiftUI out, vends its accessibility tree and draws: all 48 demo renders matched the GUI session's, PNGs pixel for pixel, and unit and UI tests passed there too.
- **A process can sandbox itself after it starts, without an entitlement.** `sandbox_init_with_parameters` with a profile that allows by default and denies the user's home works in a native host (later rules win, as in `sandbox-exec`). Declared from Swift with `@_silgen_name` it returned 0 and the process reported itself sandboxed, but nothing was denied. Called from C, the same profile denied what it should.
- **Menus are AppKit menus under Mac Catalyst.** UIKit shows an edit or context menu through `UINSMenuController` as a real `NSMenu`, whose tracking loop holds the main thread until a click: a UI test's idle wait stalled 60 s in it. A "Designed for iPad" app shows them in its own window. The runtime shows iPhone menus itself, so native hosts make AppKit's popups no-ops.
- **An iPhone-only app gets the phone idiom** on the Mac (as Mac Catalyst and as "Designed for iPad" alike), and SwiftUI's `Stepper` overflows the stack under it as soon as the app's own window draws one: the host died at launch. Adding the iPad family to the slot's `UIDeviceFamily` gives it the iPad idiom.
- **PNGs line up with the tree.** A "Designed for iPad" host drew the window's content 20 pt below the frames its tree reported (the title bar's safe area). A native host's PNGs match the tree and the simulator's layout.
- **macOS 15's UIKit is older.** On GitHub's macOS 15.7 runner (Xcode 26), `_UIHitTestContext` has `initWithPoint:radius:` and `+contextWithPoint:radius:` but no initializer that takes the event, which macOS 26 and later have. Calling the missing one threw, and AppKit's event loop swallowed the exception (the only trace was a `SOME_OTHER_THREAD_SWALLOWED_AT_LEAST_ONE_EXCEPTION` thread in a sample), so the request never got an answer. The runtime makes the context with whichever initializer exists, and catches what UIKit throws in every UI request.
- **A frame literal can lose its type.** The UI test shim gave the application element a frame as an array literal inside a `[String: Any]`, mixing `0` with `Double`s, and read it back with `as? [Double]`. Built with Xcode 26 and run on macOS 15, the cast failed and the frame was zero, so `app.swipeUp()` started at the top-left corner. The frame is a typed `[Double]` now, and frames are read as any numbers.
- **On macOS 15 a gesture container can take a swipe from a scroll view.** Over a scrollable chart, the view loop's hit test finds SwiftUI's `UIKitGestureContainer`, and with its recognizers on the touch, SwiftUI's `UIKitResponderGestureRecognizer` wins and the chart's `HostingScrollView` pan never does. The window's own hit test finds no container there, and without one the touch carries the views' recognizers and the chart scrolls. A tap still needs the container (an `onTapGesture` on an outer view goes nowhere without it), so on macOS 15 only swipes skip it. Five ways to deliver the touches were tried on the runner side by side, `_enqueueHIDEvent:` among them, which broke taps too.
- **A press-and-drag selection on a scrollable chart doesn't select on macOS 15.** With the container's recognizers the responder gesture tracks the finger (it reaches the changed state) but `chartXSelection` never changes. Stationary or same-spot move events during the press made no difference, and neither did setting the touch's precise location (`_setLocation:preciseLocation:inWindowResetPreviousLocation:`), which simless otherwise leaves at zero. On macOS 15 a chart's gestures all run inside that one `UIKitResponderGestureRecognizer`: the touch carries no recognizer of the chart's own, and after a 0.8 s hold the responder is still in the possible state, so the long press that starts a selection never fires. A finger jittering half a point every frame during the hold, held 0.8 s or 2 s, didn't change that, and neither did laying out every SwiftUI hosting view each frame during the hold (in case the hidden window's display link never ticks the graph). What that SwiftUI needs from a touch to time a long press wasn't found.
- **Binary xcframeworks in package checkouts are read-only.** SwiftPM checks packages out without write permission, and Xcode copies a framework from an xcframework with its mode, so TerraiOS's binary in the build folder was `r-xr-xr-x` and so was an APFS clone of it. Retagging failed with "cannot open". The slot's clone is made writable with `chmod -R u+w`. The build's copy stays read-only.
- **dyld doesn't look in iOSSupport for `@rpath` libraries.** TerraiOS (built for iOS 13) loads `@rpath/libswiftCoreNFC.dylib`, with `/usr/lib/swift` as its first rpath. A Mac Catalyst process finds `/usr/lib/swift/libswiftUIKit.dylib` (an absolute path) under `/System/iOSSupport`, but the `@rpath` lookup only tried `/usr/lib/swift/libswiftCoreNFC.dylib`, which macOS doesn't have, and the host died at launch. `/System/iOSSupport/usr/lib/swift` as one more rpath (`install_name_tool -add_rpath`, in the dyld shared cache, so `_dyld_shared_cache_contains_path` tells whether it's there) fixes it. Added last, it doesn't change where the libraries macOS has come from.
- **Synchronized folders can sit in classic groups.** A project that moves to Xcode 16's folders a few at a time has a classic `Abacus.AI` group with synchronized `Debug`, `ScheduledTasks` and so on inside it. The project having any synchronized folder said nothing about the kit's folder, and the build failed with "cannot find 'SimlessHost' in scope". A synchronized folder's `path` is relative to its parent group, so its real folder comes from walking the groups. Object ids aren't always 24 hex digits either (22 in that project).
- **A simulator build doesn't run as a host.** Retagging an iOS Simulator build's arm64 slices (platform 7) for Mac Catalyst, signing them ad hoc and starting the app the way a host starts loads it, but UIKit stops at launch: "_mainSceneIdentifier should have been set by now!", with the slot's Info.plist keys and the platform keys set to iPhoneOS too. So simless builds the device slice and doesn't reuse a pipeline's simulator build.
- **Two SDKs, two compiles.** Building the device slice into the DerivedData a simulator build just used took 5.7 s, against 6.4 s into a fresh one, on a small app: the module caches and products are per SDK.
- **Finding a team cost 8.5 s per `up`.** In the native mode, a project without `DEVELOPMENT_TEAM` still made simless look for a signing team: every certificate, every provisioning profile, and `system_profiler` three times. The native mode signs ad hoc and now only takes a team that's set.
- **tar keeps modification times, not change times.** After `rm -rf` and untar, a file's mtime is the original's but its ctime and inode are new. Reusing a file's digest only when size, mtime, ctime and inode all match catches a same-size edit whose mtime was put back.
- **`NSRunningApplication` sees a host started directly**, with the prohibited activation policy, and `LSBackgroundOnly` is honored without `open`. simless still finds hosts by their executable's path too, since LaunchServices registers a process a moment after it starts.

## Rendering on the Mac

- **Accessibility tree:** SwiftUI's accessibility tree is empty in-process until accessibility automation is enabled (`_AXSSetAutomationEnabled` from `libAccessibility`). Frames are in Mac screen space; take them relative to the hosting view's own accessibility frame.
- **Identifiers:** `accessibilityIdentifier` on SwiftUI elements is read through KVC; the elements don't conform to `UIAccessibilityIdentification`.
- **Dynamic Type: why text didn't scale, and the fix.** Five strategies had no effect: `.environment(\.dynamicTypeSize)`, the legacy `\.sizeCategory`, a parent trait override, window `traitOverrides`, and swizzling `preferredContentSizeCategory`. It's below SwiftUI, in CoreText: an iOS app on the Mac asks for text-style fonts with `NSCTFontTargetEnvironmentAttribute` set to the iOS-on-Mac table, which has one size per style, and `CTFontDescriptorGetTextStyleSize` is asked for platform -1. Interposing `CTFontDescriptorCreateWithTextStyleAndAttributes` (dropping that attribute, platform 0) and `CTFontDescriptorGetTextStyleSize` (platform 0) with a dyld `__interpose` section gives iOS's sizes: body is 17 pt at the default size and 53 pt at AX5, and `UIFontMetrics` scales largeTitle from 34 to 60 pt, as on an iPhone. A SwiftUI `Text` at AX5 came out 212×62.5 pt, against 212×64 in the simulator.
- **Display scale follows the hidden window's display.** On a 1× external display, layout rounds differently (whole points instead of half points). Pin `traitOverrides.displayScale = 2`.
- **Headless:** without `LSUIElement` in the Info.plist, a Dock icon flashes for ~1.5–3 s at launch. `INFOPLIST_KEY_LSUIElement` doesn't reach Designed-for-iPad builds, so set it in the built Info.plist and re-sign.
- **Windows still flash in install and test runs.** Launches by `xcodebuild test` don't carry simless's arguments. In those runs the app's main window was on screen for ~290 ms. Hiding the app early in `App.init` cut that to ~40 ms, and `LSBackgroundOnly` to ~20 ms. Only making `NSWindow` ordering (`orderWindow:relativeTo:`, `orderFront:`, `makeKeyAndOrderFront:`, `orderFrontRegardless`) a no-op removed it completely; rendering is unaffected.
- **Overriding the idiom crashes `Stepper`.** On the Mac, `traitOverrides.userInterfaceIdiom = .phone` crashes SwiftUI's `Stepper` with `EXC_BAD_ACCESS` at the stack guard. Tested one control at a time on macOS 27, `Toggle`, `Picker`, `Form`, `List` and `Form { Toggle }` render fine under it, so the crash first blamed on `Form`/`Toggle`/`Picker` came from a `Stepper` on the same screen. Size-class overrides are safe. It isn't deep recursion: the crashing thread is only 90 to 180 frames deep, frames barely repeat, and a 64 MB main-thread stack (patched into `LC_MAIN`) only moves the fault. One frame in the Swift runtime's tuple-metadata lookup asks for a huge stack allocation, which points at a SwiftUI bug. It has also been reported under the iPad idiom in a larger app, though Steppers in forms, lists, navigation stacks and with formats, sizes and locales all rendered fine under it here.
- **The phone idiom doesn't close the fidelity gap.** Against an iOS 26.5 simulator, the demo app matched in 11 of 17 renders with `.phone` and 10 of 17 with `.pad`. It fixed a split view's navigation bar, but text stayed 2–4% wider, pill buttons and `Form` toggle rows kept their Mac sizes, and `List` rows got 2 pt taller.
- **The sandbox can be opened from outside, but not by entitlement.** A slot signed with `com.apple.security.temporary-exception.files.absolute-path.read-only` fails to install ("A valid provisioning profile for this executable was not found"). A read-only sandbox extension issued by an unsandboxed process (`sandbox_extension_issue_file`, class `com.apple.app-sandbox.read`) and consumed by the app works, for both `/tmp` and `/private/tmp` spellings, and writes stay denied. Creating another app's group container from a shell fails (`Operation not permitted`), so app groups are redirected instead.
- **Several test bundles can share one launch.** `dlopen` of another `.xctest` bundle's binary from the host app at launch makes both XCTest (its default suite includes the loaded bundle's `XCTestCase` classes) and Swift Testing run its tests. Each extra launch costs the app's startup: about 1.3 s on the demo app, about 40 s on a larger app. If a test crashes in such a launch, xcodebuild restarts it without end, since it can't count the loaded bundles' tests as done.
- **Test output interleaves.** XCTest, Swift Testing and the app's own logging share one stream. Lines can start mid-line, and invisible U+200B characters show up in them, including in front of `Fatal error` and inside test names. A test's "passed" line that isn't recognized makes a finished test look hung. A parameterized test finishes as `Test name(_:) with 3 test cases passed`.
- **Hostless test bundles are dropped for Designed for iPad.** A local package's test target in the app's scheme isn't built for that destination at all, without a warning, and `-only-testing` then says it isn't in the scheme. Built for `generic/platform=iOS` and copied into the host app's `PlugIns`, the same bundle runs fine as an app-hosted bundle (XCTest and Swift Testing), including code that imports `WatchConnectivity`.
- **Extensions and watch apps install** when their ids are moved under the slot's id and each extension carries the wildcard profile and its own `application-identifier`. macOS then registers the extensions (`pluginkit -m` lists them), and `pluginkit -e ignore` hides them.
- **Measured rendering differences, from the demo app against an iPhone 17 Pro / iOS 27 simulator** (see [fidelity.md](fidelity.md)):
  - text renders 2–4% wider, which usually keeps the same line breaks.
  - `List` rows are 2 pt taller.
  - `Form` toggle rows are 6 pt taller.
  - controls use the macOS accent color.
- **VoiceOver container semantics.** An accessibility element is one unit (VoiceOver doesn't descend into it), and a container that lists `accessibilityElements` replaces its subviews. Walking subviews as well finds duplicates (a `Toggle` row's switch, a `Picker`'s value text, navigation titles) that VoiceOver never announces.
- **`.xctestrun` comes in two formats.** Schemes with a test plan produce format 2 (`TestConfigurations[].TestTargets[]`); schemes without one produce format 1, with test targets as top-level keys.
- **Device idiom:** `UIDevice.current.userInterfaceIdiom` reports `.pad` for an iOS app on the Mac, and trait overrides don't change it. `traitOverrides.horizontalSizeClass` and `userInterfaceIdiom` do change what views see through the trait collection.
- **Calibration against the iOS 27 simulator,** on a production app:
  - Simple layouts matched within 1.5 pt.
  - A two-line label wrapped differently: 334 pt wide in simless, 320 pt in the simulator, because of font metrics.
  - A `Menu` with a custom label had no accessibility label on the Mac but did on iOS.

## Hot reload

- **Compiler command lines:** Xcode no longer logs per-file compile commands (since 16.3). Reconstruct the flags from build settings instead.
- **Package checkouts contain symlink cycles.** A recursive glob loops forever; use `find`.
- **Quarantine:** files a sandboxed app writes are quarantined. `dlopen` of quarantined code makes `syspolicyd` show a **user prompt and block** the loading thread. The sandbox forbids `removexattr` of `com.apple.quarantine` (EPERM).
- **Containers:** sandbox containers are **UUID-named**; the owner is in `.com.apple.containermanagerd.metadata.plist`. They're protected as App Data. Access from another process is denied silently, with no prompt, even when it's signed by the same team. Full Disk Access is needed.
- **Occasional slow launch:** a host occasionally took ~30 s to start serving right after a unit-test run, and the cause isn't known. Restarting an instance that runs but doesn't serve (after 10 s, then 20 s, then 30 s) bounds the cost.
- **Writing to a non-existent `~/Library/Containers/<bundle id>/` path** creates a directory that containermanagerd then adopts as a protected stub, and you can't delete it from a shell afterwards.
- **InjectionNext** reports xcodebuild-only workflows broken on recent Xcode, and it targets function-body swaps. simless's approach compiles a separate module whose types shadow the app's, rebuilds fixtures from it, and needs no interposing.

## Tests on the Mac

- **App Nap slows hosts down a lot.** A host is a hidden background app, and macOS naps it: timers stretch and work runs at background priority. Reading a drawn lab report with Vision took about 40 s in a UI host and under 5 s with `beginActivity(options: [.userInitiated, .latencyCritical])`.
- **An app started with `open` may keep 256 files open.** A test run with hundreds of tests in parallel, each opening its own SQLite store, ran out ("Too many open files", Cocoa error 256). Raising `RLIMIT_NOFILE` at launch fixes it.
- **Don't spin the run loop inside a main-queue block.** UIKit and SwiftUI finish a lot of work with `DispatchQueue.main.async` (an alert's dismissal, a keyboard toolbar's hosting). Inside a main-queue block that work can't run until the block returns, however long the run loop spins. Commands run as run-loop blocks (`CFRunLoopPerformBlock`) instead.
- **SwiftUI gestures take synthesized touches once the touch knows their container.** SwiftUI's gestures (`onTapGesture`, `DragGesture`) are `UIKitResponderGestureRecognizer`s in gesture recognizer containers that aren't views. A touch built the KIF way only gets the recognizers of the views from `hitTest(_:with:)` up. `-[UIView _hitTestWithContext:]` with a `_UIHitTestContext` (point, radius, event), asked of the view under the finger, returns the deepest container, and `-[UITouchesEvent _addGestureRecognizersFromContainer:toTouch:]` adds its recognizers and its parents'. AppKit mouse events sent to the hidden window, pointer-type touches and a HID sender id didn't help.
- **Alerts and menus aren't in the app's tree on the Mac.** `UIAlertController` (and SwiftUI's `.alert`) comes up as an AppKit alert panel, a real window, through `-[NSAlert beginSheetModalForWindow:completionHandler:]`. The completion is called with a button's tag, which UIKit sets to the action's index. The completion block has to be typed as a block parameter, or Swift doesn't copy AppKit's stack block. SwiftUI's `Menu` fills its items only when the button sends `.menuActionTriggered`.
- **The keyboard toolbar is hosted by UIKit** in its text effects window, at the bottom of the screen, since there's no keyboard under it. Moving SwiftUI's accessory view into another window with a view controller crashes with `UIViewControllerHierarchyInconsistency`.
- **Windows are sized to their scene.** A second `UIWindow` in the scene covers the whole screen whatever frame it's given.
- **Vision reads differently.** The Mac's text recognition read "x10^9/L" with a superscript as "x1019/L", where the iPhone simulator reads "x10^9/L". Tests that compare OCR output exactly need a simulator.
- **The Mac answers for the Mac.** `canOpenURL` is true for `mailto:` (Mail is installed) and `WCSession.isSupported()` is false. In an iPhone simulator it's the other way round, and apps show different screens for each.
- **Compact date pickers are AppKit-style fields** (hour and minute as text fields), not a button that opens wheels.
- **XCUITest's tree isn't VoiceOver's.** `.accessibilityElement(children: .combine)` (or `.ignore`) makes one element for VoiceOver, but the children stay in the element's `automationElements` (public `UIAccessibilityContainer` API), with their identifiers, and XCUITest queries find them. When `children: .ignore` drops a Button's action from the merged element, the Button is still one of those children and can be activated.
- **A scroll view glides on after a swipe.** If the next touch comes while it's still decelerating, UIKit only stops the scroll, and a long press meant to select (Swift Charts' `chartXSelection` on a scrolling chart) then scrolls instead. Waiting for `isDecelerating` to end fixes it. The glide's last points crawl for a second or more, so a list moving under about 15 pt/s is stopped with `_stopScrollingAndZoomingAnimations` (what a landing finger does). Setting `contentOffset` doesn't end `isDecelerating`, and the next touch was still swallowed.
- **The glide comes from the speed at lift-off.** A swipe that lifts at its full 1,200 pt/s glides about 600 pt more, so one `swipeUp()` moved a list about 1,000 pt and jumped past rows that "swipe until hittable" loops look for. Easing the last fifth of the swipe down to 40% of its speed, like a finger does, keeps it under a screen.
- **Drags need a finger's pace.** Touches replayed faster than real time but stamped with a finger's timestamps still came out about twice as fast: two slow swipes moved a chart 118 days instead of about 30. UIKit evidently measures part of the velocity in real time. The moves also need to be a fixed list of small steps, each handled before the next. Placing them by the clock gave fewer, larger moves on a busy app, and a press-and-drag on a chart in a scroll view stopped selecting.
- **The Mac's stepper** names its buttons "<label>, Increment" and "<label>, Decrement" (an iPhone: "Increment" and "Decrement"), and doesn't take touches. Its element's `accessibilityIncrement()` does what a tap would.
- **Idle apps aren't idle.** An app with idle animations or timers keeps a hidden host at 8 to 10% CPU. A demo app with none sits at 0%.
- **A menu-style Picker keeps its options in its tree** as zero-size elements (from `automationElements`). `app.buttons["Dark"]` finds that copy before the open menu's row, so a tap has to go to the row that's actually on screen.
- **A toolbar `Menu` loses its items' identifiers.** In a plain `Menu`, SwiftUI sets each `UIAction`'s `accessibilityIdentifier` from the Button's. In a `ToolbarItem` the bar button's menu has none, so `app.buttons["…"]` by identifier can't find those items. Not solved yet.
- **Permission requests show macOS's dialogs.** A host is a real Mac app, so EventKit, UserNotifications, AVFoundation, Speech, Photos and the rest ask macOS, which shows its own dialog, once per bundle id (and every slot has its own). Replacing the request methods answers them in the app. Some take an integer before the completion (notification options, entity types, access levels), and a block that takes it as an object crashes on the first request.
- **Confirmation dialogs come through as AppKit alerts too,** with titles only. The `UIAlertController` behind them is still presented, with its style (action sheet) and the identifiers SwiftUI put on its actions.
- **The Mac's Swift runtime runs some debug code slower than the simulator's.** A parameterized test doing fuzzy word matching in a debug build took 180 s for its slowest case both in a simless host and as a plain macOS command-line program built with the same flags, and about 95 s for the whole test in an iOS 26.5 simulator. The time goes to the Swift runtime's generic metadata lookups (`swift_getGenericMetadata`, tuple and associated-type caches), which unoptimized generic code calls constantly. Plain CPU work (sorting, hashing, string matching) runs at the simulator's speed. `MallocSpaceEfficient=1`, which macOS sets for iOS apps on the Mac, made no difference.
- **Summed test times don't say how long a target takes.** Tests run side by side, and a main-actor test's time includes waiting for the main actor, so one target's test times added up to 10,600 s while it took about 125 s. The wall time from a target's first test to its last is what spreading targets over hosts needs.
- **Package tests can reuse the app's build.** Building a package's scheme for `generic/platform=iOS` in its own build folder compiled every module the app build had just compiled. With the app's destination (`platform=macOS,variant=Designed for iPad`), its settings and its build folder, the same build was a 21 s no-op. The app scheme's build-for-testing often builds the package's test bundles already.
- **`swift package dump-package` creates `.build`** in the package folder. `--scratch-path` sends it elsewhere.
- **`contentOffset` doesn't end a glide.** Setting it leaves `isDecelerating` true, and the next touch is still taken as a tap that stops the scroll. `_stopScrollingAndZoomingAnimations` stops it like a landing finger.
- **Deleting a preferences plist doesn't reset `UserDefaults`.** cfprefsd keeps the domain in memory, and the next launch gets the old values back. `removePersistentDomain(forName:)` from inside the app clears it. Deleting the files as well is worse: the next session's settings then vanished on every other run, so the plist files are left to cfprefsd. An app container also needs its folders (`Library`, `Library/Caches`, `tmp`, ...) to launch again, so emptying one keeps them.
- **An installed copy can stop opening.** `open` then fails with "The application cannot be opened" and POSIX error 2, for that slot only, while the files are all there. Re-registering it with LaunchServices didn't help, installing it again did.
- **A package's test build writes its own `.xctestrun`** into the build folder (`<Package>-Package_<Package>-Package_iphoneos….xctestrun`), and it sorts before the app's. Taking the first one silently dropped the app's hosted test targets.
- **"Designed for iPad" opens a `.sidebarAdaptable` tab view's sidebar**, like Mac Catalyst. iPadOS starts with the floating tab bar. Hiding the `UITabBarController`'s sidebar when it first appears matched an iPad simulator.
- **A window's safe area in a unit test host is the Mac window's**: 20 pt on top. Swapping `-[UIWindow safeAreaInsets]` for windows on the device canvas, and the root view controller's `additionalSafeAreaInsets` for the rest, gives an iPhone's 62 pt and lays the content out within it.
- **`activeProcessorCount` can change from run to run** (thermal pressure, Low Power Mode), so planning hosts on it can give a different spread for the same commit. `processorCount` doesn't.
- **On an iPad, XCUITest shows no tab bar around the floating tab bar's tabs**, and each tab is a button (an outer one and an inner one, both labeled). Checked by running the demo's tab test in an iPad simulator on iOS 26.5: `app.tabBars.firstMatch` doesn't exist there. UIKit's own automation type for `_UIFloatingTabBarItemCell` says cell, so neither traits nor that value give the iPadOS answer.
